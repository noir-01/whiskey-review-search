# 결과가 많은 검색이 느려진 이유: COLLATE와 중복 판정 조인

## 후속 변경: 중복 후보 조회 인덱스 정리

2026-09-10 로컬 DB에 적용했다. `body_hash` 계산·저장·조회와 컬럼을 제거하고, IP 일치를 후보 필수 조건에서 제외했다. IP는 참고 메타데이터로만 저장한다. 후보는 계정 ID 또는 익명 닉네임과 기간으로 좁힌 뒤 기존 본문 유사도로 비교한다. 서로 다른 익명 닉네임까지 전역 검색하는 변경은 아니다.

삭제한 기존 인덱스는 `idx_crawl_body_hash`, `idx_crawl_author`, `idx_crawl_anon`, `idx_crawl_storage`다. 작성자 단일 인덱스는 기간 조건을 포함한 복합 인덱스로 대체했고, 기타 리뷰 조인은 `idx_crawl_post_id`를 사용하는 것을 확인했다.

현재 `crawl_review_source`에는 다음 5개 인덱스만 남는다.

| 인덱스 | 컬럼 | 용도 |
| --- | --- | --- |
| PRIMARY | id | 내부 행 식별 |
| uq_crawl_source | gallery_id, post_id | 게시글 중복 저장 방지·UPSERT |
| idx_crawl_post_id | post_id | API 원본 조인 |
| idx_crawl_author_date | author_id, post_date | 계정별 기간 내 후보 조회 |
| idx_crawl_nickname_date | nickname, post_date | 닉네임별 기간 내 후보 조회 |

Docker 이미지 `noir2001/whiskey-monitor:v5`를 다시 빌드하고 중지된 `python-app`을 새 이미지로 재생성했다. 크롤링은 실행하지 않았다. 새 초기화 코드를 별도 일회성 컨테이너에서 실행하여 로컬 스키마에 반영했다.

검증: 테스트 10개 통과(IP 변경·누락과 본문 수정 후보 포함), 임시 테이블에서 마이그레이션 반복 실행 성공, 실제 DB 초기화 2회 성공, 원본 414행 유지. 후보 조회의 EXPLAIN에서 새 복합 인덱스를 확인했고, 변경 후 위스키·기타 검색 API 모두 HTTP 200이었다. `위리` 위스키 검색 결과는 31,269건을 유지했다. 아래 성능 시간은 이 후속 정리 전의 인덱스 유무 통제 실험이며, 후속 변경의 별도 성능 향상을 측정한 수치는 아니다.

2026-09-10 로컬 Docker / MariaDB 실측 기록. 최신 테스트의 방법·결과·쿼리를 이 문서 하나에 보관한다.

## 최종 통제 비교: 인덱스와 쿼리 변경 효과 분리

이전 측정은 쿼리 변경과 인덱스 추가를 동시에 적용한 비교였으므로 원인별 효과를 분리하지 못했다. 이를 보완하여 **동일 최신 이미지의 HTTP 인덱스 유무 비교**와 **SQL의 2×2 비교**를 수행했다. 블로그의 성능 개선 결론에는 이 절의 수치를 사용한다.

최신 이미지 `sha256:13a5f21707af5e699fc787f4252dd7ce25a91034952c842f1686297fbadcd486`를 태그 대신 전체 ID로 고정했다. 사용 중인 `whiskey` DB를 새 검증 DB `whiskey_perf_matrix_20260910_233018`로 복사하고, 복사본에서만 `idx_crawl_post_id`를 실제 삭제한 뒤 다시 추가했다. 두 단계 사이에 데이터와 API 컨테이너를 변경하지 않았다. SQL 세션과 API JDBC 연결 모두 query cache를 끄고, 각 조건에서 워밍업 1회와 본 측정 5회를 수행했다. 원본 DB의 인덱스는 제거하지 않았다.

### 최신 이미지 고정, 인덱스만 변경한 HTTP 비교

`위리`, `id DESC`, 첫 페이지 20건 요청. 목록과 전체 건수 조회를 포함한 API 전체 시간이며, Docker 내부 네트워크에서 측정했다.

| 최신 이미지의 인덱스 상태 | HTTP 5회 중앙값 |
| --- | ---: |
| 없음 | 4,019.12 ms |
| 있음 | 111.69 ms |

이 실험에서는 인덱스 추가로 **약 36.0배**, 약 **97.2%**의 응답 시간 감소가 관측됐다. 전체 결과 수는 양쪽 모두 31,269건이었다. JVM은 같은 프로세스를 유지했고 측정 순서는 인덱스 없음 → 있음이었다. JVM·DB 캐시 전체를 초기화하거나 실행 순서를 무작위화한 실험은 아니므로, 다른 부하에서도 동일 배율이라고 일반화하지 않는다.

### 같은 데이터에서 기존·수정 SQL × 인덱스 유무

아래는 `ANALYZE FORMAT=JSON`의 DB 내부 실행 시간 **각 5회 중앙값**이다. HTTP 시간과 직접 섞어 비교하지 않는다.

| SQL | 인덱스 | 목록 20건 | COUNT |
| --- | --- | ---: | ---: |
| 기존 | 없음 | 2,481.023 ms | 2,440.557 ms |
| 수정 | 없음 | 2,450.044 ms | 2,414.623 ms |
| 기존 | 있음 | 15.883 ms | 67.996 ms |
| 수정 | 있음 | 15.900 ms | 69.126 ms |

**`위리`에서는 인덱스 추가가 주요 개선 요인이다.** 쿼리 변경만으로 빨라졌다는 근거는 없으며, 인덱스가 있는 경우 기존·수정 SQL의 차이도 작은 실행 편차 수준이다. 네 조건에서 **31,269개 전체 ID와 순서가 모두 일치**했다.

쿼리도 변경된 것이 맞다. 저장한 기존·수정 SQL은 아래 `COLLATE` 위치만 다르다는 것을 확인했다.

```sql
-- 기존: 조회 대상 인덱스 컬럼에 COLLATE
peer_r.gallery_id COLLATE utf8mb4_general_ci = peer_cs.gallery_id
-- 수정: 반대편 값에 COLLATE, 비교 규칙은 유지
peer_r.gallery_id = peer_cs.gallery_id COLLATE utf8mb4_general_ci
```

이는 중복 그룹 내부 조회의 인덱스 사용을 개선하지만, `위리`에서는 해당 서브쿼리가 실행되지 않아 이 검색의 시간 감소를 설명하지 않는다. 네 조건의 SQL 측정은 최신 이미지에서 추출·확인한 수정 쿼리와 그 변경 전 SQL을 DB에 직접 실행한 것이며, 서로 다른 이미지 4개를 비교한 실험은 아니다.

목록 측정 중 인덱스 없는 조건에서 167ms와 191ms의 빠른 관측도 각각 한 번 있었다. 제외하지 않고 원본 배열에 보존했으며 표는 5회 중앙값이다. 이 편차의 원인은 이번 실험에서 별도로 규명하지 않았다.

## 재측정 절차

1. 이미지 전체 ID를 고정하고 리뷰·원본·중복 테이블을 별도 DB에 복사한다.
2. 복사본에서만 idx_crawl_post_id를 제거한다. 각 SQL을 워밍업 1회 후 ANALYZE FORMAT=JSON으로 5회 측정한다.
3. 같은 이미지의 API를 복사 DB에 연결하고 내부 네트워크에서 워밍업 1회 후 5회 측정한다.
4. 복사 DB에 idx_crawl_post_id(post_id)를 추가한 뒤 같은 측정을 반복한다. SQL 및 JDBC 세션의 query cache는 모두 OFF로 설정한다.
5. 전체 ID·순서·건수와 HTTP 응답의 동일성을 확인한다. 원본 DB의 인덱스는 변경하지 않는다.

요청: /api/review/whiskey?andWords=위리&sortField=id&direction=DESC&page=0&size=20

순차 요청 실험이며 동시 사용자 수용량은 미검증이다. 테스트 컨테이너는 중지했고 복사 DB에는 인덱스를 복원했다. 실행 중인 개발·LTS 컨테이너는 이 테스트에서 교체하지 않았다.

## 비교 SQL

최신 비교에 사용한 전체 SQL. 가독성을 위해 JOIN 앞에만 줄바꿈을 추가했다.

### 기존 목록

```sql
SELECT ranked.id,ranked.gallery_id,ranked.post_id,ranked.tab_key,ranked.title,ranked.recom,ranked.reply,ranked.post_date,ranked.nickname FROM (SELECT r.*,1 AS duplicate_rank FROM liquor_review r
LEFT JOIN crawl_review_source cs ON cs.gallery_id COLLATE utf8mb4_general_ci=r.gallery_id AND cs.post_id=r.post_id
LEFT JOIN review_search_duplicate sd ON sd.review_id=r.id
LEFT JOIN review_duplicate_member dm ON dm.source_id=cs.id WHERE (MATCH(r.title) AGAINST ('+위리' IN BOOLEAN MODE)) AND ((sd.review_id IS NULL OR sd.is_representative=1) AND (dm.group_id IS NULL OR NOT EXISTS (SELECT 1 FROM review_duplicate_member peer_dm JOIN crawl_review_source peer_cs ON peer_cs.id=peer_dm.source_id
JOIN liquor_review peer_r ON peer_r.gallery_id COLLATE utf8mb4_general_ci=peer_cs.gallery_id AND peer_r.post_id=peer_cs.post_id WHERE peer_dm.group_id=dm.group_id AND (COALESCE(peer_cs.published_at,TIMESTAMP(peer_r.post_date))<COALESCE(cs.published_at,TIMESTAMP(r.post_date)) OR (COALESCE(peer_cs.published_at,TIMESTAMP(peer_r.post_date))=COALESCE(cs.published_at,TIMESTAMP(r.post_date)) AND CASE WHEN peer_r.gallery_id='whiskey' THEN 0 ELSE 1 END<CASE WHEN r.gallery_id='whiskey' THEN 0 ELSE 1 END) OR (COALESCE(peer_cs.published_at,TIMESTAMP(peer_r.post_date))=COALESCE(cs.published_at,TIMESTAMP(r.post_date)) AND CASE WHEN peer_r.gallery_id='whiskey' THEN 0 ELSE 1 END=CASE WHEN r.gallery_id='whiskey' THEN 0 ELSE 1 END AND peer_r.id<r.id)))))) ranked WHERE duplicate_rank=1 ORDER BY ranked.id DESC, ranked.id DESC LIMIT 20 OFFSET 0;
```
